# 开发指导

## 两种 runner

宿主仅检查和编辑源码。安装、构建、测试、项目脚本通过 Docker runner；Docker 不可用时修复 Docker，不回退宿主执行。

| 网络 | 入口 | 设置 |
| --- | --- | --- |
| 直连默认 | `bash .agent/run.sh <命令>` | 构建/运行清空 HTTP(S)/ALL proxy，不需公司 CA |
| 宿主代理 + CA | `bash .agent/run-proxy.sh <命令>` | 读取大写/小写代理变量，大写优先；要求 PEM CA 文件 |

直连：

```bash
bash .agent/run.sh python -m tools.sync_deps
bash .agent/run.sh npm run build
bash .agent/run.sh python -m tools.dev
```

代理（export 只配置宿主环境）：

```bash
export HTTP_PROXY=http://127.0.0.1:7890
export HTTPS_PROXY=http://127.0.0.1:7890
export NO_PROXY=localhost,127.0.0.1,.localhost,.company.example
export WORKLOG_CA_CERT=/absolute/path/company-ca.crt
bash .agent/run-proxy.sh python -m tools.sync_deps
bash .agent/run-proxy.sh npm run build
bash .agent/run-proxy.sh python -m tools.dev
```

HTTPS_PROXY 通常也填 `http://`，通过 HTTP CONNECT 访问 HTTPS，以公司要求为准。代理 URL 中 loopback 主机转换为 `host.docker.internal`，Linux 添加 host-gateway。代理须允许 Docker 连接；Linux 仅监听宿主 127.0.0.1 通常不可达，需调整为 Docker 可达地址并限制访问范围。

NO_PROXY 保留原值并追加 localhost 与模拟域名；不要加入仍需经过代理的公司域名。ALL_PROXY 清空避免冲突。

`WORKLOG_CA_CERT` 为宿主信任环境导出的 PEM CA，绝对路径、不含私钥；不自动读取 macOS Keychain。构建通过 BuildKit secret 临时加载 CA，运行通过只读挂载加入系统证书，Python/pip、requests、Node/npm 使用合并信任包。建议提供一张签发 CA；多证书 PEM 需验证完整链导入结果。不关闭 HTTPS 校验。开发镜像不保留公司 CA，正式镜像不继承此配置。浏览器 CA 信任另行管理。

基础镜像拉取属于 Docker daemon / BuildKit 网络。如 Docker Hub 需代理/私有 CA，先配置 Docker Desktop/OrbStack/daemon/构建器；runner 变量不能修复此层拉取失败。CI 的 registry 与构建网络也需 Runner 管理员配置。

## 两种调试场景

优先验证真实站点单看板：将 `config/production.example.json` 复制为 `config/company.local.json`，填写真实地址后：

```bash
bash .agent/run.sh npm run build:production -- --config config/company.local.json
bash .agent/run.sh python dist/production/run.py --config config/company.local.json --database data/real-debug.sqlite3
```

4173 映射至宿主 loopback。浏览器必须经配置的 boardOrigin 访问，必要时经本地反向代理保留 Host。加载 `dist/production/extension`，登录真实 Jira/MM。代理环境将入口换为 `run-proxy.sh`。

fake 调试执行上面的 `npm run build` + `python -m tools.dev`，在一个开发容器内监督三个子进程。访问 `http://board.localhost:4173`，加载 `dist/extension-dummy`；在 `http://jira.localhost:4180/jira/__dummy/` 与 `http://mattermost.localhost:4181/__dummy/` 登录 Alice/Bob。多身份使用独立浏览器 profile。数据库 `.tmp/worklog.sqlite3` 与生产卷分开；Ctrl+C 停止服务、保留数据。

三容器 fake 部署见[执行与部署](执行与部署.md#fake-环境显式选择)。探针使用 `npm run build:probe` + `python -m tools.dev --probe`，不进入生产包。

## 验证与依赖维护

```bash
bash .agent/run.sh python -m tools.sync_deps
bash .agent/run.sh python -m pytest tests/backend -q
bash .agent/run.sh npm run typecheck
bash .agent/run.sh npm run test:unit
bash .agent/run.sh npm run generate:api:check
bash .agent/run.sh python -m tools.verify_boundaries
bash .agent/run.sh npm exec -- playwright install chromium
bash .agent/run.sh npm run test:e2e
```

E2E 前停止占用 4173/4180/4181 的调试进程；测试使用隔离数据库。实际公司接入另行手动验收。

修改 Python `.in` 后，通过 runner 中的 `python -m piptools compile --allow-unsafe --strip-extras --generate-hashes --output-file requirements/runtime.txt requirements/runtime.in` 生成 runtime 锁；同样生成 dev 锁，再 `tools.sync_deps`。Node 通过 runner 中 npm 更新，提交 package-lock。不要把测试依赖加入 runtime。

runner 检测锁变化会要求同步。`.agent/run.sh app` 仅保留兼容转发，部署使用明确的 Compose 或 `docker.sh` 入口。

镜像和 Compose 本地验证使用 `bash .agent/run.sh docker <参数>`：此分支只在宿主调度 Docker，构建和应用代码仍在容器内执行，不安装开发依赖，也不应用 run-proxy 的网络转换；镜像构建的代理参数由 Docker/BuildKit 配置管理。
