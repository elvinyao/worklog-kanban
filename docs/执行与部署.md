# 执行与部署

## 入口总览

| 场景 | 入口 | 服务 / 数据 |
| --- | --- | --- |
| 正式部署（优先） | CI 根 Dockerfile → 根 compose.yaml | 仅 board，已有真实 Jira/MM，生产数据卷 |
| fake 三服务部署 | deploy/fake/compose.yaml | board + fake Jira + fake MM，独立 fake 卷 |
| 开发调试 | .agent/run.sh 或 run-proxy.sh | 临时开发容器，详见开发指导 |
| 旧版源码部署 | docker.sh / 四个 .command | 保留旧状态、备份恢复工具，首次默认 fake |

## GitLab CI 构建

`.gitlab-ci.yml` 先在 MR、默认分支及 tag 运行类型/契约检查、Vitest、开发构建、完整后端测试及 Playwright。测试镜像复制允许的源码和示例配置，不绑定宿主检出目录，不需要 Registry 凭据或 `WORKLOG_SITE_CONFIG`。本地验证步骤见[开发指导](开发指导.md)。

测试通过后，默认分支及 tag 构建正式镜像，推送 `$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA`，并交付相同配置的扩展 artifact。不自动登录部署主机，不部署 fake。

前置条件：GitLab Container Registry、Linux Docker executor、允许 privileged 的 DinD Runner；Runner 配置 `[runners.docker]` 需要 `privileged = true` 及 `volumes = ["/certs/client", "/cache"]`，供 job 和 Docker service 共享 TLS 客户端证书。对应[GitLab 官方 DinD 指导](https://docs.gitlab.com/ci/docker/docker_in_docker/)。镜像架构跟随 Runner，需与部署机匹配；当前不自动构建多架构。

在 GitLab Settings → CI/CD → Variables 创建 **File 类型**变量 `WORKLOG_SITE_CONFIG`，内容按 `config/production.example.json`：

```json
{
  "mode": "production",
  "boardOrigin": "https://board.company.example",
  "jiraBaseUrl": "https://jira.company.example/jira",
  "mattermostBaseUrl": "https://chat.company.example"
}
```

使用 protected 变量时，运行构建的分支/tag 也必须 protected。配置只有公开地址，不放 Token、密码或 Cookie；三个地址会嵌入镜像与扩展。boardOrigin 只能是 origin，工作台部署在域名根路径；Jira/MM 可有 context path。

CI 以 BuildKit secret 传入配置，并以配置 SHA256 使构建缓存随地址变化失效。安装依赖使用 Python 哈希锁和 npm ci。构建后校验生产配置/资产及不含 fake、Node，再推送镜像；扩展位于 artifact 的 `dist/ci/extension`。artifact 默认保留 30 天，正式发布时应长期归档与镜像对应的扩展。

当前按环境构建：改三个地址后重新运行 CI，部署新镜像及对应扩展。相同 commit 重跑可能覆盖 tag，发布后建议在部署配置使用 registry 的 `@sha256:...` digest 固定版本。公司 Runner 若需要代理与 CA，需分别配置 DinD 拉取和 BuildKit 构建网络；本机调试代理脚本不自动作用于 CI。

## 只部署看板

部署主机仅需 Docker + Compose v2，以及仓库的 `compose.yaml` 和按 `deploy/production.env.example` 创建的 `.env`，不需要 Python、Node、源码、fake 或开发依赖。

`.env` 示例：

```dotenv
WORKLOG_IMAGE=registry.gitlab.company.example/team/worklog-kanban@sha256:实际镜像摘要
WORKLOG_BIND_ADDRESS=127.0.0.1
WORKLOG_PORT=4173
```

部署主机使用以下 Docker 编排命令；开发仓库内调试这些操作时可加 `bash .agent/run.sh docker ...` 前缀：

```bash
docker login registry.gitlab.company.example
docker compose --env-file .env config
docker compose --env-file .env pull
docker compose --env-file .env up -d --wait
docker compose ps
docker compose logs --tail=100 board
```

默认项目名 `worklog-kanban-prod`，数据卷 `worklog-kanban-prod_board-data`，数据库 `/data/board.sqlite3`。保持项目名不变；改变项目名会使用新卷。默认端口仅绑定宿主 loopback，通过公司反向代理发布到 boardOrigin。若代理在别的容器，需设计共享网络或可达绑定地址，不能把另一个容器的 127.0.0.1 当宿主。

反向代理保留原 Host，转发到本机 4173，支持 SSE 长连接、关闭缓冲、合理设置读超时，HTTPS 在入口终止。看板访问控制由公司入口负责。服务健康检查自动按镜像配置设置 Host；直接用不匹配的 IP/Host 访问会被拒绝。

默认忽略转发 IP。要保留客户端 IP，在 Compose override 的 `command` 中完整保留 `python /opt/worklog/release/run.py --config /opt/worklog/release/site-config.json --database /data/board.sqlite3`，再追加 `--trusted-proxy <容器实际看到的代理IP/CIDR>`；禁止信任所有网络，代理须覆盖伪造转发头。

用户从 CI artifact 解压扩展，按[用户指导](用户指导.md)手动加载。容器无需连接真实 Jira/MM；浏览器需要访问并登录这两个系统。

## 更新、停止、备份与恢复

更新前备份，修改 `.env` 镜像 digest，再执行 `pull` 和 `up -d --wait`。Compose 不提供自动事务回滚；失败时检查日志和数据库版本。旧镜像可能不兼容升级后的库，不要只回退镜像就认为已恢复。

```bash
docker compose stop
docker compose start --wait
docker compose down
```

stop/down 保留卷；**不要使用 `down -v`**，除非明确要永久清空数据。

新 Compose 不生成旧管理工具的 `.tmp/docker-state`，不要混用 `docker.sh backup/restore`。正式包提供 `maintenance backup/check/restore`，使用同版本镜像和内置站点配置。先创建宿主 `backups` 目录并允许 UID 10001 写入；每次备份使用新的目录名（下面的 `release-before-upgrade` 是示例）。部署主机执行以下命令；仓库内操作加 `bash .agent/run.sh docker ...` 前缀：

```bash
docker compose stop board
docker compose run --rm --no-deps -v "$PWD/backups:/backup" --entrypoint python board /opt/worklog/release/run.py maintenance backup --config /opt/worklog/release/site-config.json --output /backup/release-before-upgrade
docker compose run --rm --no-deps -v "$PWD/backups:/backup:ro" --entrypoint python board /opt/worklog/release/run.py maintenance check --config /opt/worklog/release/site-config.json --backup /backup/release-before-upgrade
docker compose start --wait board
```

备份包含独立 `board.sqlite3` 和 `manifest.json`，校验 SHA256、站点配置指纹、schema、SQLite 完整性/外键、看板版本和卡片数量。已有输出目录不会覆盖。应用仍运行时，数据库锁拒绝备份/恢复。失败后先检查原因，不要为了目录权限改用 root。将完整备份目录、对应镜像 digest、Compose、站点 JSON 与扩展一起异地保存；备份包含共享数据，不包含个人预览。校验和用于检测损坏，不提供来源认证。

先用临时目录演练（不会改 `/data`，容器退出即清除演练数据）：

```bash
docker compose run --rm --no-deps -v "$PWD/backups:/backup:ro" --entrypoint python board /opt/worklog/release/run.py maintenance restore --config /opt/worklog/release/site-config.json --backup /backup/release-before-upgrade --database /tmp/drill/board.sqlite3
```

正式恢复：

```bash
docker compose stop board
docker compose run --rm --no-deps -v "$PWD/backups:/backup:ro" --entrypoint python board /opt/worklog/release/run.py maintenance restore --config /opt/worklog/release/site-config.json --backup /backup/release-before-upgrade
docker compose start --wait board
```

若在同一终端连续执行维护操作，可定义临时 shell 函数减少重复路径输入（与上方完整命令等价）：

```bash
worklog_maint() {
  local mode="${1:-ro}"; shift
  docker compose run --rm --no-deps -v "$PWD/backups:/backup:${mode}" --entrypoint python board \
    /opt/worklog/release/run.py maintenance "$@" --config /opt/worklog/release/site-config.json
}
# 用法示例：
# worklog_maint rw backup --output /backup/release-before-upgrade
# worklog_maint ro check --backup /backup/release-before-upgrade
# worklog_maint ro restore --backup /backup/release-before-upgrade
```

仅在恢复命令成功后启动。恢复先验证私有副本，再将当前数据库及 WAL/SHM 原样保存至 `/data/before-restore-<UUID>/`（即使当前库已损坏），移除旧 sidecar 并原子替换主库。命令输出 `previousFiles` 是保留位置；确认恢复正确前不要删除。中断会留下 `/data/board.sqlite3.maintenance`，服务拒绝启动，文件中记录首次保留目录；保留它并用已校验备份重新执行恢复，不要手工删除标记绕过检查。恢复完成后核对数据并刷新所有浏览器。旧版裸 SQLite/旧管理器备份需沿用对应版本工具，不得手工伪造 manifest。

## fake 环境（显式选择）

```bash
bash .agent/run.sh docker compose -f deploy/fake/compose.yaml build board
bash .agent/run.sh docker compose -f deploy/fake/compose.yaml up -d --wait
bash .agent/run.sh docker compose -f deploy/fake/compose.yaml cp board:/opt/worklog/dist/extension-dummy dist/extension-fake
bash .agent/run.sh docker compose -f deploy/fake/compose.yaml stop
```

首次导出前确保本地 `dist` 目录存在（正常开发构建会创建它）。仅 fake Compose 有三个服务，默认项目 `worklog-kanban-fake`，卷 `worklog-kanban-fake_board-data`。加载导出的扩展，访问 board.localhost:4173、jira.localhost:4180/jira/__dummy/、mattermost.localhost:4181/__dummy/。后两者登录 Alice/Bob，不使用真实凭据。模拟会话在容器重启后需重新登录。

fake 与生产端口冲突时将生产 WORKLOG_PORT 改为 4174，并对应调整反向代理。fake 的域名/端口是固定开发配置，不能单改端口映射。停止保留数据；删除容器用同一 `-f` 的 `down`，不加 `-v`。

## 已有部署的兼容与迁移

`docker.sh` 和四个 `.command` 保留，直接调用 `docker/manage.sh`；已有 `.tmp/docker-state/<项目>/compose.json`、卷及 backup/restore 命令继续有效。它们使用 `docker/legacy.Dockerfile`，不会变成拉取 CI 镜像的入口。详细历史操作见[旧运行说明](运行说明.md)。

旧 root Compose 的默认项目是 `worklog-kanban`，新生产和 fake 使用不同项目名，不会自动接管或删除旧卷。不要直接对旧项目执行新 Compose 来尝试迁移。先通过旧工具备份并停止旧 board，保留旧卷；在新项目恢复一致数据库副本，核对 schema、站点和共享数据后再切换入口。同一数据库不能同时由新旧实例写入。旧管理器导出的 manifest 不应伪造给新流程使用。

根 Dockerfile 的专用 ignore 文件优先于通用 ignore，依据 [Docker 构建上下文说明](https://docs.docker.com/build/concepts/context/)；正式镜像和 fake 构建上下文分别管理。
